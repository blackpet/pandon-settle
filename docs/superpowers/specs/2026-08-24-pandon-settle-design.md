# 판돈정산 설계서 — 아키텍처 · 저장 · 배포

- 작성일: **2026-08-24**
- 대상: `SPEC.md`(기능 명세)를 어떤 구조로 만들고 어디에 올릴지
- 상태: **1~5장 확정 대기 없음 / 6장 미결 항목은 확인 필요**

`SPEC.md`가 "무엇을 만드는가"를 정한 문서라면, 이 문서는 "그것을 어떤 구조로 만들고 어디에 올리는가"를 정한다. 기능·계산 규칙·화면 문구는 이 문서에서 다루지 않는다.

## 0. 확정된 전제

브레인스토밍에서 사용자가 직접 고른 값들이다. 아래 설계 전부가 이 네 줄에서 나온다.

| 전제 | 값 | 여기서 따라 나오는 것 |
|---|---|---|
| 누가 보는가 | **총무 폰 1대만** | 서버·로그인·실시간 동기화가 전부 불필요해진다 |
| 데이터 수명 | **한 판(하룻밤) 단위로 끝**, 공유는 카카오톡·메시지 전송 | 누적 조회가 없으므로 데이터베이스가 필요 없다 |
| 배포처 | **Cloudflare** | 같은 계정의 `inklore` 관행을 따른다 (3장) |
| 개발 기간 | **3일** | 도구 세팅에 쓸 시간이 없다. 프레임워크·네이티브 앱 탈락 |

## 1. 웹앱이냐 앱이냐 — 웹앱(PWA)

**결론: 설치형 앱을 만들지 않는다. 브라우저에서 도는 웹앱으로 만들고, 폰의 "홈 화면에 추가"로 앱처럼 쓴다.**

3일이라는 기간이 이 판단을 거의 혼자 결정한다. 스토어에 올리는 앱은 코드를 다 짜도 그다음이 문제다.

| 항목 | 네이티브 앱의 현실 |
|---|---|
| iOS 배포 | Apple Developer 계정 연 $99 + **심사 1~3일** |
| Android 배포 | Play Console 등록비 $25 + 심사 |
| 친구 폰에 깔기 | 심사 통과 전에는 TestFlight 초대 같은 별도 절차 |

기간을 빼고 봐도 네이티브를 골라야 할 이유가 없다. **이 앱은 카메라·푸시알림·백그라운드 실행·연락처를 하나도 쓰지 않는다.** 네이티브만 할 수 있는 일이 없다.

반대로 홈 화면에 추가한 웹앱이 주는 것은 실사용에서 앱과 구분되지 않는다.

- 홈 화면 아이콘 · 주소창 없는 전체화면 실행
- 비행기 모드·지하에서도 동작 (서비스 워커가 파일을 캐시한다)
- **설치 절차가 없다** — 링크 하나 보내면 친구도 그 자리에서 쓴다

나중에 마음이 바뀌어 스토어에 올리고 싶어지면, 이 코드를 Capacitor 같은 껍데기로 감싸는 길이 그대로 남아 있다. **지금 결정이 그 선택지를 닫지 않는다.**

## 2. 기술 형상 — Vanilla JS · 빌드 없음

**결론: 프레임워크와 빌드 도구를 쓰지 않는다.** `SPEC.md` 1장이 정한 그대로다.

검토했던 대안은 Vite + Preact/Svelte였다. 화면 갱신이 자동이 되는 대신 도구 세팅·PWA 플러그인·파일 구조 재설계에 **반나절이 사라진다.** 화면이 다섯 개뿐인 앱에서 그 거래는 손해다. 기간이 2주였다면 다시 볼 만하다.

빌드를 없앤 대가로 "화면 갱신을 손으로 관리해야 한다"는 부담이 생기는데, 이건 5장의 렌더링 방식으로 해소한다.

### 파일 구조

`SPEC.md` 1장의 구조에서 **한 가지가 달라진다.** 앱 파일들이 `public/` 아래로 내려간다.

```
pandon-settle/
├── SPEC.md · README.md · LICENSE
├── wrangler.jsonc          ← 배포 형상 (3장)
├── package.json            ← 도구만. 번들러·트랜스파일 없음
├── docs/superpowers/specs/ ← 이 문서
├── public/                 ← ★ 이 폴더만 배포된다
│   ├── index.html
│   ├── styles.css
│   ├── manifest.json
│   ├── sw.js
│   └── src/
│       ├── rules.js        ← 게임별 점수→금액 (순수)
│       ├── settle.js       ← 최소 송금 정산 (순수)
│       ├── store.js        ← 상태 보관 + localStorage
│       ├── chart.js        ← SVG 누적 그래프
│       └── ui.js           ← 화면 렌더링 · 이벤트
└── test/
    ├── rules.test.js
    └── settle.test.js
```

**왜 `public/`을 뒀나.** 배포할 파일과 배포하면 안 되는 파일을 폴더 하나로 가른다. 전부 저장소 맨 위에 두면 Cloudflare에 올릴 대상을 지정할 자리가 없어 **명세서·테스트·내부 문서까지 통째로 공개된다.** 제외 목록(`.assetsignore`)을 관리하는 방법도 있지만, 그건 새 파일이 생길 때마다 사람이 기억해야 하는 규칙이다. 폴더 경계는 기억할 필요가 없다.

> ⚠️ `SPEC.md` 1장의 파일 구조 그림과 이 구조가 어긋난다. 6장 미결 항목 4번 참조.

`package.json`에는 명령 세 개만 둔다. **번들러도 트랜스파일도 없으므로 "빌드 없음"은 그대로 참이다** — wrangler 버전을 못 박고 테스트를 한 줄로 돌리기 위한 것이다.

```json
{
  "scripts": {
    "test":   "node --test test/",
    "dev":    "wrangler dev",
    "deploy": "wrangler deploy"
  }
}
```

## 3. 배포 — Cloudflare Workers (Pages 아님)

**결론: Cloudflare Workers의 정적 자산(Static Assets) 기능으로 `public/` 폴더를 그대로 올린다. Worker 코드는 한 줄도 쓰지 않는다.**

### 왜 Pages가 아닌가

같은 계정의 `../inklore` 프로젝트를 확인한 결과가 이 판단을 뒤집었다. **inklore에는 Pages 프로젝트가 하나도 없다.** 앱 세 개(`relay_server`, `errors_server`, `legal_site`)가 전부 Worker이고 전부 `wrangler deploy` 한 줄로 나간다.

그중 `legal_site`는 **데이터베이스도 상태도 없이 문서 두 편만 서빙하는** 앱이라 판돈정산과 처지가 사실상 같은데, 그것조차 Worker다.

그리고 지금은 **실행할 코드 없이** 폴더만 올리는 게 가능하다. 설정에서 `main`(실행할 코드 파일)을 생략하고 `assets.directory`(올릴 폴더)만 적으면 Cloudflare가 그 폴더를 그대로 서빙한다. *(설치된 wrangler 4.121의 설정 스키마에서 `main`이 필수 항목이 아니고 `assets`가 정식 키인 것을 확인했다.)*

| 이유 | 내용 |
|---|---|
| 집안 규약이 하나로 | 이 계정의 배포 명령·인증·설정 파일 형식이 전부 `wrangler.jsonc` + `wrangler deploy`로 통일된다. 판돈정산만 다른 도구를 쓸 이유가 없다 |
| 코드가 필요 없다 | `legal_site`처럼 TypeScript를 짤 일이 없다. 폴더만 가리키면 끝 |
| Cloudflare의 현재 방향 | 신규 프로젝트 권장이 Workers 쪽으로 옮겨갔다 |
| 나중에 막히지 않는다 | 서버 기능이 필요해지면 설정에 `main` 한 줄로 확장된다. Pages였다면 Functions로 갈아타야 한다 |

### 환경은 하나만 둔다

inklore의 두 서버는 `-local` / `-dev` / 운영 세 갈래로 쪼개져 있다. 그건 `--env`를 빠뜨린 배포가 **운영 데이터를 엉뚱한 저장소에 흘려보내는 사고**를 막는 장치다.

판돈정산에는 **덮어쓸 데이터 자체가 없어서 그 사고가 성립하지 않는다.** 반대로 환경을 나누면 공개 주소만 두 개가 되고, 낡은 판이 계속 살아 있는 쪽이 더 위험하다. `legal_site`가 정확히 같은 이유로 환경을 안 나눴고(그 파일 주석에 근거가 적혀 있다), 그 판단을 따른다.

배포 명령은 `--env` 없는 `npx wrangler deploy` 하나다. 주소는 도메인 없이 **`https://pandon-settle.blackpet.workers.dev`** 가 나온다.

### 설정 파일

```jsonc
// wrangler.jsonc
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "pandon-settle",
  // 프로젝트를 만든 날로 한 번 박고 그 뒤로 건드리지 않는다. 이 값을 올릴 때마다
  // 런타임 동작이 달라질 수 있어서, 재배포가 코드 변경 없이 결과를 바꾸게 된다.
  // (inklore 세 앱이 모두 만든 시점 날짜에 고정돼 있다 — 그쪽은 2026-07-01.)
  "compatibility_date": "2026-08-24",

  "assets": {
    "directory": "./public",       // 이 폴더만 세상에 나간다
    "not_found_handling": "none"   // 화면 전환이 페이지 안에서 일어나 라우팅이 없다
  },

  // 도메인 없이 관리형 HTTPS 주소를 받는다.
  // 서비스 워커(오프라인 동작)는 HTTPS에서만 도므로 이게 PWA의 필수 조건이다.
  "workers_dev": true,
  // 버전마다 영구 주소가 생기면 되돌린 뒤에도 옛 판이 계속 열린다.
  "preview_urls": false,

  "observability": {
    "enabled": true,
    "logs": { "invocation_logs": false },
    "traces": { "enabled": false }
  }
}
```

`observability`의 두 `false`는 로그 양 조절이 아니라 **방문 기록을 남기지 않겠다는 설정**이다. 술자리에서 누가 얼마 잃었는지가 남는 앱이라 플랫폼 자동 로그(방문 IP·시각)까지 끈다. inklore의 세 앱이 모두 같은 형태로 선언한다.

### 배포를 1일차에 한 번 미리 돌린다

빈 `index.html` 하나로 주소를 살려 둔다. 마지막 날 시간에 쫓기며 처음 배포하다 막히는 상황이 사라진다.

배포 후 확인은 **실제 폰**에서 한다 — 홈 화면에 추가 → 비행기 모드 → 뜨는가.

## 4. 모듈 경계와 데이터 흐름

**세 층으로 나누고, 아래층은 위층을 모른다.**

| 층 | 파일 | 아는 것 / 모르는 것 |
|---|---|---|
| **계산** | `rules.js`, `settle.js` | 숫자만 안다. 화면도 저장소도 **모른다** |
| **상태** | `store.js` | 상태를 들고 있고 저장한다. 계산 규칙은 **모른다** |
| **표현** | `ui.js`, `chart.js` | 상태를 읽어 그린다. 계산을 **하지 않는다** |

`rules.js`와 `settle.js`가 앱의 심장이고 나머지는 껍데기다. 이 둘은 브라우저 없이 `node --test`로 완성할 수 있다.

### 한 판이 기록되는 과정

```
사용자가 탭 (승자 → 점수 → 배수 칩)
   │
   ▼  ui.js 가 입력을 모아 "라운드 초안"을 만든다
   │
   ▼  rules.js 가 계산한다  →  deltas = [+2700, -1800, -900]
   │       (초안 + 룰 설정 + 점당 금액 → 금액 배열. 순수 계산)
   │
   ▼  미리보기에 표시한다   ← 아직 저장하지 않는다
   │
   ▼  [확인] 을 누른다
   │
   ▼  store.addRound({ ...초안, deltas })
   │       └ localStorage 에 즉시 저장 + 구독자에게 알림
   │
   ▼  ui.js 가 상태를 다시 읽어 화면을 다시 그린다
```

**계산이 두 번 일어나지 않는다.** 미리보기에서 나온 `deltas`를 그대로 저장한다. 그래서 "미리보기와 확정 금액이 다르다"가 구조적으로 불가능하다.

### 함수 경계

```js
// rules.js — 순수. DOM·localStorage 참조 금지
compute(round, rules, pointValue) -> number[3]   // round.game 으로 분기
  computeGostop / computePoker / computeHoola

// settle.js — 순수. rules.js 를 모른다
balances(rounds, n = 3) -> number[]              // 라운드를 접어 잔액
settle(balances)        -> { from, to, amount }[]
```

`settle.js`가 `rules.js`를 모르는 것이 중요하다. 게임이 3종에서 5종으로 늘어도 **정산 코드는 한 글자도 안 바뀐다.** 정산은 "잔액 배열"만 보면 되기 때문이다.

모든 계산 함수는 반환 직전에 `assertZeroSum(deltas)`를 통과해야 한다. 어긋나면 저장하지 않고 에러를 던진다 (`SPEC.md` 4장 불변식).

## 5. 저장 · 렌더링 · 테스트

### 5-1. 저장 — localStorage 하나

**결론: `localStorage`에 상태 전체를 JSON 한 덩어리로 넣는다. 키는 `pandon-settle:v1`.**

**SQLite를 안 쓰는 이유.** SQLite가 답이 되는 조건은 "몇 달치를 쌓아두고 지난 기록을 질의한다"인데, 0장에서 **한 판 단위로 끝난다**로 정해졌다. 조건이 성립하지 않는다.

| | localStorage | 브라우저용 SQLite |
|---|---|---|
| 데이터 크기 | 24판 × 3명 = 몇 KB. 한도(5MB)의 0.1% | 같은 데이터에 엔진 1MB |
| 필요한 조회 | "이번 판 전부 읽기" 하나뿐 | 쓸 일이 없는 질의 능력 |
| 3일 일정 | 세팅 0분 | 엔진 로딩·저장소 초기화에 반나절 |
| "빌드 없음" | 유지 | 정면 충돌 |

**저장 시점: 모든 상태 변경 직후 즉시.** `store.js` 안의 모든 변경 함수가 마지막에 저장을 부른다. **화면 코드에서 저장을 호출하는 자리를 만들지 않는다** — 그래야 "저장을 빠뜨렸다"가 구조적으로 불가능해진다.

**잔액은 저장하지 않는다.** 라운드 목록을 매번 접어서 구한다(`balances()`). 저장된 잔액과 라운드가 어긋날 자리 자체가 없고, 실행취소가 `rounds.pop()` 한 줄로 끝난다.

**버전이 다를 때.** 마이그레이션 함수를 태우고, 실패하면 **데이터를 지우지 않고** `pandon-settle:backup:{시각}` 키로 옮긴 뒤 새로 시작한다.

**저장이 아예 안 될 때** (사파리 프라이빗 모드 등). 저장 호출을 `try/catch`로 감싼다. 실패하면 앱을 죽이지 않고 메모리에서만 돌리되, **화면 위쪽에 "저장이 꺼져 있습니다" 경고를 계속 띄운다.** 조용히 실패하면 폰이 잠긴 사이 하룻밤 기록이 통째로 날아간다.

### 5-2. 렌더링 — 상태가 바뀌면 화면을 통째로 다시 그린다

```js
store.subscribe(() => render(store.state));
```

프레임워크 없이 화면 갱신을 관리하는 방법이다. **일부만 골라 고치지 않는다.** 화면에 있는 것이 잔액 3개, 칩 몇 개, 미리보기, 버튼 몇 개라서 다시 그리는 비용이 사람 눈에 보이지 않는다. 대신 **"상태는 바뀌었는데 화면 한구석이 옛날 값"** 이라는 부류의 버그가 통째로 사라진다.

**이벤트는 컨테이너 하나에 위임한다.** 버튼마다 핸들러를 붙이는 대신 바깥 상자에서 한 번 받아 `data-action` 속성으로 분기한다. 화면을 다시 그려도 핸들러를 다시 붙일 일이 없다.

**다시 그리면 안 되는 두 가지 예외:**

1. **입력 중인 숫자 칸** (훌라 잔여점수). 통째로 다시 그리면 커서와 입력 중이던 값이 날아간다. → 입력값을 상태에 즉시 반영하고, 다시 그린 뒤 커서 위치를 복원한다.
2. **움직이는 것** (잔액 숫자 롤링, 토스트). 통째로 그리면 매번 처음부터 다시 시작한다. → 잔액 숫자는 값만 갈아 끼우는 별도 함수로 뺀다.

**화면 전환은 상태 필드 하나**(`state.screen`)로 한다. 주소(URL) 라우팅을 쓰지 않으며, 그래서 3장의 배포 설정이 `not_found_handling: "none"`이다.

### 5-3. 테스트 — 계산층만

`node --test`로 `rules.js`와 `settle.js`만 검증한다. 브라우저 테스트는 만들지 않는다 — **3일 안에서 브라우저 테스트 하네스를 세우는 비용이 그것으로 잡을 버그의 값어치보다 크다.** 화면은 실제 폰에서 눈으로 본다.

`SPEC.md` 11장에 **이미 검증이 끝난 기대값 표**가 있다. 그대로 케이스로 옮기면 계산은 테스트만으로 완성된다.

모든 케이스에 자동으로 걸리는 공통 검사를 헬퍼로 묶는다:

- `deltas`의 합이 정확히 **0**
- `deltas`의 모든 원소가 **정수** (원 단위. 부동소수점 금지)
- 3인 정산 결과가 **2건 이하**
- 송금액 합계 = 플러스 잔액 합계

## 6. 3일 일정과 미결 항목

### 일정

| | 하는 일 | 끝나면 |
|---|---|---|
| **1일차** | 저장소 형상(`public/`·`wrangler.jsonc`·`package.json`) → **빈 페이지로 배포 1회** → `settle.js` → `rules.js` 3게임 → 테스트 | 주소가 살아 있고, **화면 없이 계산이 완성된다** |
| **2일차** | `store.js` → 홈·세팅·고스톱 입력·정산 화면 → 카카오톡 공유 | **이 시점부터 실전 투입 가능** |
| **3일차** | 훌라·포커 입력 화면 → PWA(홈 화면 추가·오프라인) → 실제 폰 점검 | 친구들에게 링크를 뿌릴 수 있다 |

**3일 밖으로 미루는 것** (자르는 게 아니라 순서를 뒤로 둔다):

- SVG 누적 그래프 (`chart.js`)
- 통계 기록 (최고 한 판 / 승률 / 피박 최다)
- **룰 설정 편집 화면** — 설정 값 자체는 코드에 있고 모든 계산이 그것을 거친다. `SPEC.md`의 "배수 규칙 하드코딩 금지" 원칙은 지켜지며, **손으로 고치는 화면만** 나중이다

### 미결 항목 — 구현 전 확인

1. **포커를 실제로 어떻게 치는가** (`SPEC.md` 12장 1번). 칩을 쓴다면 판마다 입력하지 말고 "끝날 때 최종 칩 개수만 입력"이 압도적으로 편하고, 그러면 포커 화면이 완전히 달라진다. **확정 전까지 `simple` 모드만 만든다.**
2. **고박일 때 개인 배수 처리** (`SPEC.md` 12장 2번). 현재 정의는 고박자 본인 배수만 적용. 쳐보고 어색하면 조정.
3. **게임 도중에 종류를 바꾸는 것을 허용할까** (`SPEC.md` 12장 3번). 라운드마다 `game` 필드가 있어 기술적으로는 이미 가능하다. **허용 권장.**
4. **`SPEC.md` 1장 파일 구조를 이 문서(2장)에 맞춰 고칠 것인가.** 앱 파일이 `public/` 아래로 내려간 것이 반영돼 있지 않다. 명세서를 정본으로 유지하려면 갱신이 필요하다.
